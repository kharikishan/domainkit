# Notifications

## Data Models

`Notification`: `id`, `userId`, `type` (see below), `referenceType` (task/project/sprint), `referenceId`, `message`, `read` (boolean, default false), `createdAt`.

`NotificationPreference`: `userId`, `type`, `channel` (in-app/email), `enabled`. One row per user per type per channel. Missing rows default to enabled.

**Notification types:** `task.assigned`, `task.status_changed`, `task.commented`, `task.due_soon`, `project.member_added`, `project.status_changed`, `sprint.started`, `sprint.completed`, `mention`.

## Business Rules

**Delivery channels:**
- `in-app`: Always created as a `Notification` record. The frontend polls `/api/notifications?unread=true` or uses a WebSocket subscription.
- `email`: Dispatched via job queue (not inline). Email delivery is best-effort — failures are logged but do not block the originating action.

**Digest mode:** If a user has not been active (no API calls) for more than 15 minutes, subsequent notifications are batched and sent as a single digest email when the batch reaches 5 items or after 30 minutes, whichever comes first. Per-user `lastActiveAt` is updated on every authenticated request.

**Preference defaults:** All notification types are enabled on all channels by default. Users can mute specific types per channel. A preference row with `enabled: false` suppresses that channel for that type.

**Self-notification suppression:** Do not send a notification to the user who triggered the event. If Alice assigns a task to herself, she does not receive a `task.assigned` notification.

**Read state:** Mark-as-read is per notification. There is also a `POST /api/notifications/mark-all-read` bulk operation that marks all unread notifications for the authenticated user as read.

## API Surface

`GET /api/notifications` — list notifications for authenticated user; filter with `?unread=true`, `?type=`.
`PUT /api/notifications/:id/read` — mark single notification as read.
`POST /api/notifications/mark-all-read` — mark all as read.
`GET /api/notification-preferences` — get all preferences for authenticated user.
`PUT /api/notification-preferences` — upsert preferences; body is array of `{ type, channel, enabled }`.

## Gotchas

- Never deliver email synchronously in the request path. Always enqueue a job. Email providers impose rate limits that will cause timeouts under load.
- The `referenceId` field is a UUID with no FK constraint — notifications can outlive the task or project they reference. Always handle the case where the referenced entity no longer exists when rendering.
- Digest batching requires a reliable scheduled job. If the job fails, notifications are not lost (they remain in the `Notification` table) but email delivery may be delayed indefinitely. Monitor job queue depth.
- `mention` notifications are generated by the comment system (not in this domain) but delivered here. Ensure the comment module calls the notification service interface, not the database directly.

## Testing Priorities

1. Self-notification suppression across all event types.
2. Preference override: verify a muted channel produces no delivery for that user/type pair.
3. Digest batching: mock clock to trigger both the count threshold (5) and time threshold (30 min).
4. Mark-all-read atomicity — concurrent requests should not duplicate unread counts.
5. Rendering with deleted reference: notification for a deleted task should not 500, should render gracefully.
